# 校园资源服务平台 MVP 产品设计

版本：0.1；日期：2026年10月10日

校园资源服务平台以自习座位预约为核心，连接整教室预约审批和物业报修。首版采用 Web 应用，围绕三个业务模块各完成一条可用流程，并验证教室占用、维修下架和恢复可预约之间的联动。

本版面向课程项目的首个可演示迭代。需求依据为2026年10月8日[《软件过程管理与工程伦理》课程实践项目任务书](taskbook.pdf)；后续功能继续保留在需求清单中，MVP 不等同于期末完整交付范围。

## 产品目标与用户

首版帮助学生找到并使用可预约的座位，让教室审批和维修状态及时影响座位可用性，同时建立可测试、可部署、可追溯的开发基础。

| 用户 | 主要需求 |
| --- | --- |
| 学生 | 搜索座位、预约、签到、查看个人记录、上报故障 |
| 具有教室申请权限的用户 | 提交整教室预约申请、查看进度、撤销申请 |
| 审批与运营管理员 | 审批申请、维护空间数据、派单及验收 |
| 维修人员 | 查看分派的工单、更新维修进度、提交完工 |

同一账号可具备多个角色，具体操作由权限控制。

## MVP 功能范围

| 模块 | 首版主要功能 |
| --- | --- |
| 公共层 D | 预置账号登录；固定角色与服务端权限校验；院系访问限制；教室、座位、插座标记与开放时间的基础维护；关键操作日志 |
| M1 自习座位预约 | 按教室、时间、插座条件搜索可用座位；按整点小时预约，单次默认最多4小时；取消预约；输入每日教室码签到；开始15分钟后未签到自动取消、释放座位并记录违约；查看当前预约和历史 |
| M2 整教室预约与审批 | 有权限的用户提交申请；管理员单级审批通过或驳回；查看状态、撤销自己的申请；审批通过后占用该教室对应时段的全部座位 |
| M3 物业报修工单 | 上报教室故障；管理员人工派单；维修人员更新为维修中、提交完工；管理员验收；查看工单状态 |
| 跨模块联动 | 教室审批通过后阻止对应时段的个人预约；工单进入维修中后整室下架；申请撤销或工单验收通过后解除对应限制；保留限制的来源和关联记录 |

## 核心业务流程

1. **座位预约**：学生搜索可用座位 → 提交预约 → 到场后输入教室码签到 → 查看预约记录。开始15分钟后仍未签到的预约自动取消，座位释放并产生一条违约记录。
2. **整教室预约**：具有权限的用户提交申请 → 管理员审批 → 通过后对应时段的全部座位不可被个人预约；驳回不形成占用，撤销后解除该申请的占用。
3. **物业报修**：用户上报故障 → 管理员派单 → 维修人员进入维修中，整室座位下架 → 提交完工 → 验收通过，解除该工单的维修限制。

## 主要业务规则

- 同一座位在同一时段只能有一个有效预约；并发提交也应遵守该规则。
- 预约必须位于教室开放时间内。院系专属自习室只对本院系用户开放，单次预约时长上限作为系统参数管理。
- 申请提交时不占用座位。整教室审批通过前检查已有个人预约，存在时段冲突则不能通过。
- 报修进入“维修中”才触发整室下架；提交完工后，需验收通过才能解除维修限制。
- 每次解除限制只影响对应申请或工单。仍存在其他维修工单、整教室占用或个人预约时，座位不能错误恢复为可预约。
- 座位可用性保留 M1 个人预约、M2 教室审批占用、M3 维修下架的来源。用户只能查询和操作权限范围内的记录。

临时维修对已有预约的处置方式、预约取消截止时间和签到有效时间窗，在实现前补充到对应功能的验收标准中。

## 后续迭代范围

| 方向 | 后续功能 |
| --- | --- |
| 座位服务 | 历史一键复用、运营统计；预约前15分钟提醒、开始后10分钟未签到提醒及取消通知；邮件或微信推送 |
| 教室审批 | 多级审批、超时自动撤销、更细的申请资格规则 |
| 报修服务 | 图片附件、超时升级、维修评价 |
| 公共能力 | 自定义角色与权限配置、完整配置后台；按接入条件评估校园统一登录 |
| 附加功能 | 核心系统稳定后，可按进度增加通过公开接口操作业务的自然语言 Agent |

后置的课程要求仍需在期末前完成；校园统一登录、图片附件等扩展能力按实际需要安排。

## 首版交付与验收方向

首版应能演示上述三条业务流程，并验证重复预约被拒绝、未签到自动释放、审批占用、维修下架以及解除限制后的正确恢复。

工程交付随功能同步推进：需求和验收标准纳入版本管理；数据库结构使用版本化迁移脚本，初始化数据脚本可重复执行；关键行为与跨模块联动有实际测试；提交触发自动构建和测试，通过后自动部署测试环境；部署版本可追溯到提交。

跨模块联动通过真实接口实现，尽早完成至少一条后端模块之间经过网络的 HTTP 调用链路。生产环境人工审批发布、版本标记和回滚能力纳入后续交付计划，并在期末实际演示；不能用前端分别调用两个端点替代模块间网络调用。

开发顺序为公共数据与权限 → M1 预约主流程 → M2 和 M3 简版 → 跨模块联动验收。基础与接口约定明确后，三个模块可并行开发。
